# 从一个地点到一个游园搭子

## 1. 形成最小简报

复用用户已有信息，记录：地点与类别、希望解决的体验问题、到访日期与时间、入口和出口、总时长、必看与可选点、同行者明确提出的需要、已有资料、希望的交付物。未提供年龄或同行关系时，不默认亲子口吻。

用户只说「做一个植物园搭子」时，可以先创建演示工作台、列出资料清单，再补真实地点。用户给了真实园区与三小时预算时，围绕这个约束整理资料，别擅自扩大为城市旅行平台。

可用的产品简报：

```text
地点：____    核心体验：____
来访情境：____    可用时间：____
入口 / 出口：____    想看：____
移动或感官需要（用户明确提供）：____
已有官方资料：____    资料日期：____
这次交付：陪逛方案 / 本地工作台 / 可部署应用
暂时无法核实：____
```

## 2. 把地点拆成三层

| 层 | 内容 | 关键判断 |
| --- | --- | --- |
| 空间 | 入口、场馆、展区、出口、步行连接 | 实际可达，不能穿墙、穿湖或跨未开放区域 |
| 知识 | 物种/藏品、个体故事、设计意图、保育/历史背景 | 来源、时间、授权、对应场馆 |
| 体验 | 看什么、怎么问、没遇见怎么办、留下什么记录 | 能在现场完成，不妨碍他人和动物 |

先用 3–8 个地点做小闭环，数量只是起步建议，不是上限。完整园区可以后来再加。

## 3. 生成地点包

遵循 [place-pack.md](place-pack.md)。选择清楚可核验的来源，把事实拆成小条目。路径时间需说明依据：官方指引、获许可的地图、现场测量或明确标注的估计。示意坐标只影响画面，不用于计算行走距离。

不能核实的时候，先交付资料草稿和缺口表；允许真实包 `facts: []`，网页会显示尚无故事资料。来源不足时不要复制演示事实充数。路线不连通时仍可查看资料卡，规划会明确报告不可达。

## 4. 工作台与 Agent 分工

模板只依赖本机 Node.js。Agent 先运行 `scripts/dudu.mjs init`，再读取并修改生成目录的 `pack.json`。已有完整地点包时使用 `--pack` 直接生成。

- 浏览器：表单、确定性路线估计、查看资料、记录和导出。
- Agent：检索资料、核对来源、回答追问、改写讲解、整理手帐、修改工作台。
- 可选服务：网页内问答、语音、图像识别、共享观察。这些按需求另接。

不要通过 `--name 北京某公园` 把虚构园区当成已经完成的真实应用。保留 `mode: demo`，直到地点、连接和来源被替换。

## 5. 交付与实测

先运行结构校验，再打开实际工作台。用「首次到访，只有三小时，中途少了一小时」走通流程，检查是否保留出口路程；用「暂时没看见」检验替代体验；写一条自己的观察，验证导出能保留原意。

实地测试时记录偏差：实际步行用时、无法到达的路径、过长的讲解、错误或过时事实、触发打扰、拍照与记录是否妨碍观察。先修复事实和可达性，再优化视觉和玩法。

交付描述应包含：打开方式、当前可用功能、资料更新时间、已知缺口、数据存放位置。只有用户明确要发布或已有发布授权时才部署公开站点。
